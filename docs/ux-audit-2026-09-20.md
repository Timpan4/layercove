# LayerCove browser and pod-log audit

Date: 2026-09-20. Target: https://layercove.timpan.dev/.

## Outcome and scope

Basic print monitoring is not reliable enough to tell an operator whether a job is printing or why it is waiting. The slicer workbench cannot display the tested model placement or its completed preview. Several primary actions and monitoring fields are clipped at phone width.

The audit used the user's signed-in Helium session through the browser extension, which identifies itself as Chrome. Desktop observations include 1440 × 900 and the normal 2355 × 1322 viewport. Phone observations use a 390 × 844 viewport; some checks also used mobile device metrics. This is responsive browser testing, not validation on physical Android or iOS hardware.

The contract was to inspect the basic model-to-print and monitoring flows on desktop and mobile, record reproducible UI issues, and inspect the application pod logs in Kubernetes context `wall-e`. This report distinguishes inspected interfaces from completed operations. It does not claim every possible defect or every administrative setting was tested.

One test slice of the existing `Voron_Design_Cube_v8.STL` completed through File Manager and created `Voron_Design_Cube_v8_TPU_43m28s.gcode`, shown as 3.3 MB and 43 minutes. The file remains in the library. No physical print was started, paused, stopped, or cancelled. Printer settings, plate-clear state, queue entries, and cluster resources were not deliberately changed. The user's existing working-tree edits were preserved.

## Findings that block or mislead basic use

### 1. A stale printing queue row blocks the next assigned job

**Impact:** The operator cannot determine why an idle printer is not starting its queued job or find the clearing action described by the setting.

**Reproduce:** Open Print Queue and inspect `Voron_Design_Cube_v8_PLA_25m0s.gcode`, assigned to Tim Voron. It shows Pending and ASAP. Open printer controls: Tim Voron is idle/ready. Open Settings → Workflow → Queue & Dispatch: Require plate-clear confirmation is unchecked. Its help says disabling it also hides the plate-status badge and clearing button.

**Log evidence:** The scheduler repeatedly reports `printer 1 not available — connected=True, state=idle, awaiting_plate_clear=True`. This log records state, not the guard that rejected dispatch. Code inspection showed that the Moonraker idle check returns before the Bambu plate-clear gate. The busy-printer set is instead seeded from existing printing queue rows. No explicit clearing action was present on the inspected Voron card.

**Database evidence (read-only, September 21):** Queue item 5 remained printing with started_at September 19 09:33:59 UTC and start_reconcile_after NULL. Its provider correlation and remote filename were present. The existing recovery scan excluded rows with a cleared deadline, leaving the following assigned item blocked by the busy-printer set.

**Required behavior:** Reconcile accepted jobs after missed terminal events using fresh provider telemetry and exact job identity. Do not declare success from idle telemetry or retry start commands automatically. Display a waiting reason on the pending row.

### 2. Dashboard status and progress contradict detailed printer controls

**Impact:** The primary monitoring screen can suggest a busy machine is available.

**Reproduce:** On Printers, inspect DOGGE'S PRINTER. The fleet card and focus header say Ready, the card says Ready for next job, and the focus panel says Printing at 0%. Open controls: the same printer shows Printing at 70%, later advancing its layer counter. Return to the dashboard: it still presents Ready/0% and suggests Choose a file to print. Selecting the Printing filter retains a card labelled Ready.

**Required behavior:** Derive fleet badges, focus state, percentage, availability and suggested action from consistent printer telemetry. Represent missing values as unknown rather than ready or zero.

### 3. Queue state does not establish whether the printer accepted the job

**Impact:** The user's reported uncertainty about uploading/queuing is visible in the current UI.

**Reproduce:** Print Queue lists `Voron_Design_Cube_v8` under Currently Printing at 0%, with Stop Print available. The printer controls show Tim Voron Idle, No active job. The other Voron item remains Pending. Neither row presents a transfer stage, printer acknowledgment, last confirmed update, or an actionable waiting reason.

**Required behavior:** Distinguish queue acceptance, file transfer, printer acknowledgment, starting/heating, actual printing, completion and failure. Show transfer progress when available, an indeterminate state when it is not, and a reason/recovery action for a blocked job. Reconcile stale archive/queue state with live printer state.

**Boundary:** No new print dispatch was submitted during the audit. Missing upload-stage feedback is also user-reported; the existing stale/contradictory state was reproduced directly.

### 4. Filament-related requests fail with `PrinterSnapshot.raw_data`

**Impact:** Inventory/loaded-filament calculations and historical AMS recording fail during ordinary browsing and background collection.

**Evidence:** Current app logs contain repeated `AttributeError: 'PrinterSnapshot' object has no attribute 'raw_data'`. The request traceback passes through `backend/app/api/routes/printers.py:2264`, `get_inventory_remain`, into `backend/app/services/print_scheduler.py:1160`, `_build_loaded_filaments`, at `status.raw_data.get("ams_extruder_map", {})`. Background AMS history recording reports the same missing attribute.

**Required behavior:** Make consumers use the supported printer snapshot contract and expose a recoverable unavailable state on request failure. Add regression coverage for both the route and background collector when fixing this. Do not suppress the exception and silently report zero filament.

### 5. Workbench reports ready/completed with no placement or preview

**Impact:** Users cannot inspect the model or verify the generated toolpath before printing.

**Reproduce:** Open `/slicer/workbench?library_file=16&job=21`. Select Tim Voron and `Voron 2.4 300 0.4 nozzle - my · 0.4 mm · tool 0`. The selected process and filament appear and Readiness becomes ready. Prepare still says bed geometry is unavailable and asks for `printable_area` and `printable_height`. The footer shows completed and 0 objects. Preview says Slice plate to generate preview. Print remains disabled.

**Required behavior:** Load the selected machine's usable bed geometry and the source model. Restore the completed job's preview or state clearly why it is unavailable and offer a working recovery path. A ready/completed label must not imply that placement or preview is usable when neither is loaded.

**Boundary:** The existing historical workbench job was tested. A separate File Manager slice succeeded and produced G-code, so this is not evidence that all slicing execution fails.

### 6. Slicer workbench is not usable at phone width

**Impact:** Preparation and preview controls cannot be reliably reached or understood.

**Reproduce:** At 390 × 844, the workbench header gives space to Undo/Redo, Slice again and Print while Prepare/Preview are obscured. The settings `aside` measures 400 CSS pixels wide within a 390-pixel viewport and consumes the visible working area. The screenshot shows clipped selectors and no usable model canvas alongside it.

**Required behavior:** Provide a phone layout with accessible Prepare/Preview navigation, a settings drawer or separate panel, and a usable full-width model/preview area. Keep primary actions visible without overlapping controls.

### 7. Mobile monitoring focus panel clips important telemetry

**Impact:** Phone users lose the job name, remaining-time area and right-hand telemetry while monitoring a print.

**Reproduce:** At 390 × 844, select a printer and scroll below its fleet card to the camera/current-job panel. The long job name and right-hand fields extend beyond the visible panel edge. The document width can still equal the viewport width because the inner content is clipped.

**Required behavior:** Allow grid children to shrink, wrap long filenames, and stack telemetry at narrow widths. Do not treat a matching document `scrollWidth` as proof that inner panels fit.

### 8. Primary actions overflow off-screen on multiple mobile pages

**Impact:** Common tasks appear unavailable on phones.

**Reproduce at 390 × 844:** File Manager's header shows Generate Thumbnails and Link External while later actions, including Upload, lie to the right. Spool Inventory shows Import/Export with Add Spool off-screen. Project details show Export while Edit lies beyond the right edge. Shared catalog selection can horizontally shift content so that the left of the page title and cards is clipped.

**Required behavior:** Wrap header actions or place secondary actions in an accessible menu, keeping Upload/Add/Edit visible. Keep tab navigation scroll within its own strip instead of shifting the page content.

## Other reproduced issues

### 9. Unknown filament remaining is displayed as negative stock

The dashboard shows PLA -1%, PLA -1%, ABS -1%, and PETG -1%. These sentinel-looking values are not useful stock readings. Render unknown/unavailable explicitly and distinguish it from empty. The backend failure above may be related, but that causal link was not proven.

### 10. Reprint dialog gives AMS-oriented guidance for the external-spool Voron

Select the Voron archive, open Print, select Tim Voron, and expand Filament Mapping. It says Type not found and Required filament type not found in printer, with a Select slot control containing no selectable slots. Print remains enabled. This leaves the operator uncertain whether the warning is advisory, a real incompatibility, or missing telemetry. Use backend-capability-aware material confirmation for external-spool printers and make blocking versus advisory warnings explicit.

### 11. Archive availability labels contradict file availability

Several Bambu archives show 0 B, a GCODE badge whose description says Sliced file - ready to print, and a disabled Print button. A page-level notice explains that source files could not be retrieved, but each affected card still claims readiness and offers preview/download actions. Distinguish metadata-only archives from downloadable/reprintable artifacts on the card itself.

### 12. Mobile library menus and shared modal accessibility need correction

File-card menu buttons have no accessible name; several mobile selection actions are also unnamed. Opening the login password-recovery modal in the initial unauthenticated browser left focus on the triggering button behind it, provided no dialog semantics, exposed an unnamed close button, and did not respond to Escape. The authenticated queue edit and print modals also exposed unnamed close buttons and left focus on their triggers when opened.

Name icon buttons by action, label dialogs and move focus inside them. Verify focus containment and return focus on dismissal. The login-specific checks were performed before switching to Helium; they are not a Helium authentication test.

### 13. Diagnostic advice names the wrong camera protocol/port

System → System Health labels a chamber-image timeout as RTSPS port 322 unreachable and tells the user to open port 322. The evidence printed directly below it is a chamber-image timeout on port 6000. This sends troubleshooting toward the wrong port for the observed failure. Match recovery advice to the actual printer camera protocol and error.

### 14. Phone zoom is explicitly disabled

The page's viewport meta includes `maximum-scale=1.0, user-scalable=no`. This is especially unhelpful with small text and clipped controls. Permit zoom and retain responsive layout. Actual pinch behavior was not tested on a physical phone.

Other observed evidence:

1. The scheduler repeatedly reports the idle Voron unavailable with `awaiting_plate_clear=True`.
2. `PUT /api/v1/slicer/catalog/preferences` returned 422 at 21:11:15 UTC. The invalid field was not present in the captured evidence, so its cause remains unproven.
3. `POST /api/v1/library/files/16/slice` returned 202 at 21:16:41 UTC for the audit's slice; the output subsequently appeared in File Manager.
4. Camera capture on the Bambu chamber-image port timed out during startup. An Obico snapshot failed. A live camera image was later visible in the browser, so the startup failures do not prove a continuing camera outage.
5. Bambu MQTT disconnected and disabled request-topic subscription after an early disconnect. The browser later showed live telemetry.
6. FTP listing `/timelapse` returned 502 during startup.
7. The namespace warning event concerns the old `layercove-57d4c958-59n84` pod exiting during replacement, not a crash of the current pod.
8. No Orca sidecar log lines were returned for the deployment-to-audit interval. This is absence of emitted log evidence, not proof that the sidecar has no defects.
9. Tailscale emitted startup TPM/sysctl/resolv.conf warnings and subsequently reported healthy startup/connectivity signals. These were not established as causes of the reproduced UI failures.

## Unproven or blocked paths

1. Actual printer upload, transfer failure/retry, dispatch acknowledgment, physical start, pause/resume, stop and completion require an explicitly coordinated print test. No such command was sent during this audit.
2. The first mobile Slice-menu attempt closed without visible feedback. Desktop retry opened the slice modal and completed slicing. Treat the first attempt as an inconclusive observation, not a separately established defect.
3. MakerWorld downloading is gated by Bambu Cloud sign-in. No credentials or account settings were changed.
4. Native phone browser behavior, touch gestures, virtual keyboard and file-picker behavior remain unverified.
5. The existing workbench job did not yield a preview, so layer scrubbing, object transforms and print-from-preview could not be validated.
6. Administrative features such as authentication management, API keys, backups, destructive cleanup and external notification delivery were outside the basic-use execution scope.

## Recommended correction order

1. Repair the snapshot consumer failures and stale printing queue records. Preserve the physical safety guard and make its state visible.
2. Reconcile dashboard, queue and printer telemetry; expose transfer/dispatch stages and actionable errors.
3. Restore workbench model, bed and completed-preview loading, then verify model-to-G-code-to-printer with a coordinated test print.
4. Correct phone layout for the workbench, monitoring panel and primary action bars.
5. Correct missing-data labels, printer-capability-specific filament guidance, icon/modal accessibility and camera diagnostic advice.

The initial audit did not change the application. The follow-up code changes below are local PR work; production has not been deployed or altered.
